# Chapter 15 — Memory Hierarchy, Revisited for Triton

## 15.1 What This Chapter Is and Isn't

You already know the GPU memory hierarchy from your CUDA background: global memory (HBM, large and slow), the L2 cache, shared memory/SRAM (on-chip, fast, explicitly managed in CUDA), and registers (fastest, per-thread). This chapter doesn't re-teach that hierarchy — it maps the vocabulary you already have onto **what you can now actually go look at**, using Chapter 14's tools. Every concept here has a concrete, inspectable counterpart in TTGIR, PTX, or a compiled kernel's own metadata — this chapter's job is to show you exactly where.

## 15.2 Global Memory and Coalescing: Where Layouts Actually Matter

Recall the layout encoding from Chapter 14, §14.4 — `sizePerThread = [2, 2], threadsPerWarp = [8, 4], warpsPerCTA = [2, 4]`. This isn't just bookkeeping metadata; **it is, concretely, the thing that determines whether your `tl.load`/`tl.store` calls become coalesced global-memory accesses or not.** The layout says exactly which thread owns which elements of a tile; if the compiler assigns a layout where consecutive threads own consecutive memory addresses, the resulting hardware access is coalesced — a single wide memory transaction serving many threads at once, the same coalescing concept from CUDA, just chosen for you rather than by hand.

This is also where a badly-shaped access pattern can quietly cost you performance without ever producing a wrong answer. A transposed or strided load (Chapter 5) is always *correct* — Triton will generate valid code for it regardless of layout — but if the natural memory layout doesn't allow consecutive threads to touch consecutive addresses, the compiler cannot manufacture coalescing that isn't there; you'll get correct, uncoalesced (and therefore slower) global-memory traffic. You won't diagnose this from reading Python — you'll diagnose it with the profiling tools in Chapter 22, informed by knowing (as you now do) that the layout encoding is where this decision actually lives.

## 15.3 Shared Memory: Implicit Allocation, and What It's Actually For

In Triton, (cite index="39-1">shared memory management, grid/block sizing, and register allocation are all implicit</cite> — you never write a CUDA-style `__shared__` declaration. The compiler decides, chiefly, that `tl.dot`'s operands need to be **staged through shared memory** before being fed into tensor-core MMA instructions, and allocates exactly what's needed for that automatically.

You've already used the *measurement* of this without necessarily connecting it to the mechanism: `kernel.metadata.shared` (Chapter 7, §7.5) is the literal shared-memory footprint, in bytes, that this specific compiled kernel actually allocated — the same value that fed directly into the occupancy calculation there. Now you know what it structurally represents: the compiler's own answer to "how much on-chip shared memory does staging this kernel's `tl.dot` operands (and any other shared-memory-resident intermediate) actually require."

Recall also, from Chapter 14's citation of real TTGIR layout kinds, that AMD's gfx942 target was assigned a layout called **`amd_rotating_shared`**, alongside the more general **`swizzled_shared`** layout present on other targets. Swizzling here is doing exactly the job you already know from CUDA: rearranging *which* shared-memory bank a given address maps to, so that multiple threads accessing shared memory in the same cycle, at strides that would otherwise collide on one bank, don't actually contend — the identical bank-conflict-avoidance problem, solved automatically by the compiler's layout choice rather than by manual padding/index tricks.

## 15.4 Registers and the Occupancy Trade-off, Formalized

Registers hold everything actively "live" during a program instance's computation — loaded tile data, intermediate results, and (very concretely, from Chapter 9–10) the `float32` accumulator across an entire `K`-loop. The more of these that need to be simultaneously live, the more registers per thread the compiled kernel requires — larger `BLOCK_SIZE_M`/`BLOCK_SIZE_N` tiles, wider accumulators, and more concurrently-resident intermediate tensors all push this number up directly.

Here's the mechanism behind the occupancy calculation you already implemented by hand in Chapter 7, §7.5, stated plainly: **an SM's register file is a fixed, finite budget, shared across every warp resident on it at once.** If each thread needs more registers, fewer threads' worth of warps can be simultaneously resident — occupancy drops as a direct, mechanical consequence of register usage per thread, not as some separate tunable dial. This trade-off has a long history in GPU programming under the name **occupancy cliff**: a kernel whose register usage per thread crosses a threshold can see occupancy drop sharply and discontinuously, because the number of warps that fit is a step function (an integer number of warps' worth of registers must fit, not a smooth fraction) — the classic illustration of this, from CUDA's earlier hardware generations, is a kernel whose register usage per thread happens to allow only a handful of warps to co-reside on one SM, where a small increase in per-thread register count drops that number by a whole warp at once, not gradually.

**An honest, important nuance, worth internalizing rather than glossing over**: (cite index="42-1">the relationship between register pressure, occupancy, and performance is non-monotonic and workload-dependent</cite> — more occupancy is not automatically better. A memory-bandwidth-bound kernel (like Chapter 7's softmax) genuinely benefits from high occupancy, because more concurrently-resident warps means more opportunities to hide memory latency behind other warps' work. A kernel that's already latency-hidden through other means — for instance, software pipelining via `num_stages` (Chapter 6, Chapter 14 §14.4), which overlaps loads with compute *within* a single program instance — may see little additional benefit from further occupancy, because the latency it would hide is already being hidden a different way. Treat "maximize occupancy" as a useful default heuristic, not an unconditional goal — Chapter 22's profiling work is where you'll learn to tell these cases apart empirically rather than by assumption.

## 15.5 Register Spilling: What It Is, and How to Actually Detect It in Triton

When a program instance's live register needs genuinely exceed what the hardware can provide per thread (or exceed what the compiler is willing to allocate at a given target occupancy), the excess values are **spilled** — written out to a region called "local memory" which, despite the name, is physically backed by the same global DRAM as everything else. This is **correctness-preserving but performance-destroying**: (cite index="41-1">register pressure exceeding the SM's per-thread limit forces the compiler's backend to spill to local memory, adding load/store traffic that is correct but genuinely costly</cite> — data you believed lived in a register, at register latency, is quietly round-tripping to HBM instead.

**Detecting this in Triton specifically:**

- **`kernel.n_regs`** — registers actually used per thread, the same value the Chapter 7 occupancy calculation relies on.
- **Spill information** — Triton surfaces this by forwarding `ptxas`'s own verbose compilation diagnostics; a real, production example makes the failure mode vivid: an actual Triton-generated matmul kernel was reported spilling (cite index="36-1">24 bytes of spill stores and 24 bytes of spill loads in one configuration, and as much as 472 bytes of spill stores in another, for functions named `triton_gemm_dot_2` and `triton_gemm_dot_3753`</cite> in a real deployed pipeline — this is not a hypothetical risk invented for this chapter; it is a documented, encountered problem in real Triton-compiled GEMM kernels.

**A genuine caveat worth knowing before you trust these numbers blindly**: Triton's spill reporting has a documented quirk — (cite index="35-1">kernels using `tl.sin`/`tl.cos` have been observed to always report a nonzero spill count, even when the underlying computation is otherwise simple, unlike `tl.exp`/`tl.log`/basic arithmetic, which don't exhibit this</cite>. The lesson isn't "don't trust spill counts" — it's "treat a nonzero spill count as a strong signal worth investigating, not an infallible ground truth." When a reported number surprises you, the reliable next step is exactly what Chapter 14 taught you: pull `kernel.asm['ptx']` (or the final SASS, if you have `cuobjdump`/`nvdisasm` available) and look directly for `ld.local`/`st.local` instructions — the literal, static evidence of spilling, independent of any summary metric Triton or `ptxas` chooses to report.

This connects to a subtler point about the pipeline stages from Chapter 14: (cite index="42-1">the register count visible in PTX bears little relation to the final SASS register count — PTX has not yet been through the backend's actual register allocation, so the real story only becomes visible after `ptxas` (or the AMD equivalent) has run</cite>. If you inspect `kernel.asm['ptx']` expecting to see the *final* register pressure, you're looking one stage too early — `ptxas`'s conversion of PTX into the loadable `cubin` (Chapter 14, §14.6) is where register allocation actually happens.

## 15.6 A Cross-Backend Nuance: AMD's Register Pools

The official fused-softmax kernel's own source code contains a direct, citable caveat about backend portability that's worth reproducing here rather than letting you discover it the hard way: (cite index="37-1">on AMD's CDNA architectures, the register budget used for an occupancy calculation represents general-purpose VGPRs specifically — accumulation VGPRs, used by matrix instructions, are drawn from a separate pool</cite>, and this split isn't always present in the same way across every generation. The practical consequence: the occupancy formula you built by hand in Chapter 7, §7.5 — total registers divided among concurrently-resident warps — needs this adjustment on AMD hardware; a register budget computed as if every register were fungible will be wrong specifically for kernels that use AMD's matrix instructions heavily. This is a concrete, specific instance of the portability theme Chapter 13 introduced — not every memory/register concept translates identically across vendors, and this is exactly the kind of detail Chapter 26 will return to systematically.

## 15.7 A Forward-Looking Aside: Spilling Into Shared Memory

Worth a brief, honest mention since it's genuinely recent: in CUDA 13.0 (released 2025), NVIDIA introduced (cite index="34-1">shared-memory register spilling — an optimization that reduces spill latency and L2 pressure for register-heavy kernels by spilling into on-chip shared memory rather than local/global memory, enabled via a PTX pragma, and shown to eliminate spilling entirely in at least one sample kernel with a measured 7.76% reduction in kernel duration</cite>. This is, as described, a raw CUDA/PTX-level feature — this chapter is describing the hardware and compiler landscape Triton sits on top of, not asserting that Triton has already wrapped this specific mechanism as a first-class kernel-writer-facing knob. If register spilling is a genuine bottleneck in a kernel you're optimizing, checking Triton's current documentation (or its release notes) for whether this has since been exposed is a reasonable, current thing to do — a good example of exactly when to reach for a live web search rather than assume this curriculum's snapshot is still complete.

## 15.8 A Diagnostic Recipe

Putting this chapter together into something you can actually run through on a real kernel:

1. **Check `kernel.n_regs` and `kernel.metadata.shared`**, and compute occupancy using Chapter 7 §7.5's formula — remembering the AMD VGPR-pool caveat (§15.6) if you're on ROCm.
2. **Don't trust a spill-count summary alone** — pull `kernel.asm['ptx']` (Chapter 14, §14.7) and grep for `ld.local`/`st.local` as the ground-truth, static check, especially if the kernel uses `tl.sin`/`tl.cos` or anything else you haven't already confirmed against this quirk.
3. **If occupancy is low and spilling is present**, the first things to try are exactly the knobs you already control: smaller `constexpr` tile sizes, a narrower accumulator where numerically safe, or a different `num_warps`. Re-measure — don't assume a fix worked without confirming via `n_regs`/spill-grep again.
4. **Remember occupancy isn't the whole story** (§15.4) — a bandwidth-bound kernel benefits from more of it; a kernel already latency-hidden by pipelining may not. Chapter 22 gives you the profiling tools to tell these apart with real measurements rather than assumption.

Then check the actual PTX for `ld.local`/`st.local` in both. Report whether you observe the same discrepancy described in §15.5, and reflect on what this tells you about trusting summary metrics versus static ground truth.

**Exercise 3 — Sweep `num_warps` and watch occupancy respond.** For a kernel of your choice, compute occupancy via Chapter 7's formula across a small range of `num_warps` values, holding everything else fixed. Confirm `n_regs` and the resulting occupancy calculation move together the way §15.4 describes, and identify whether you can find an "occupancy cliff" — a point where a small change in configuration causes a disproportionate drop.

**Exercise 4 (optional, requires ROCm) — Reconcile the AMD VGPR nuance.** If you have access to AMD hardware, inspect a matrix-instruction-heavy kernel's reported register usage there, and reason through how §15.6's general-purpose-vs-accumulation-VGPR split would change your occupancy calculation compared to treating all registers as fungible.

**Exercise 5 — Cross-target occupancy, without needing every GPU.** Using Chapter 14 §14.7's GPU-free compilation technique, compile the *same* kernel for two targets with meaningfully different register-file sizes or architectural generations, and compare the resulting occupancy calculations. Confirm that hardware generation alone can shift occupancy substantially even with byte-identical kernel source — direct, hands-on reinforcement of Chapter 14's "same input, different compiled reality" theme, applied here specifically to registers rather than instruction selection.
